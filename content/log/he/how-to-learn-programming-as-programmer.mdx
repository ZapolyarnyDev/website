## הרעיון המרכזי

המחשבה הפשוטה הראשונה, שכבר השתרשה בקהילה: אי אפשר ללמוד תכנות כמו שצריך רק מצפייה בקורסים,
קריאת תיעוד או חזרה על מדריכים. כל אלה מועילים, אבל כשלעצמם לא הופכים אדם למתכנת.

אגיד אפילו יותר: למידה בסגנון ״עכשיו אלמד את יסודות השפה, ואז אולי אכתוב אפליקציית TODO עם פריימוורק״ תפריע לאיש המקצוע לעתיד.

לדעתי, הרווח הגדול ביותר למתכנת הוא לקחת משימה לא ברורה, ורצוי קשה מאוד, ולהפוך אותה לצעדים קטנים ומובנים.
מניסיוני, אחר כך מתחיל המחזור המתיש ביותר: קוד -> הרבה טעויות -> מבינים -> משפרים את הפתרון.

המטרה של למידה כזאת היא לא רק לקבל מוצר מוכן או להכיר את התחביר של השפה שאנחנו לומדים, אלא לזכור את הדרך לפתרון המשימה
או, למשל, ללימוד פריימוורק חדש.

בקצרה:

- לא ללמוד שפה בנפרד ממשימות;
- לא להעתיק קוד בלי להסביר כל שורה;
- לא לנסות לכתוב מושלם מיד;
- לקרוא קוד של אחרים בקביעות;
- לשכתב את הפתרונות שלכם אחרי שמבינים את כל השלבים;
- להסיק מסקנות על הדרך שבה הגענו לפתרון ועל מה שהפריע קודם;
- לתעד טעויות כחומר לצמיחה.

## הלמידה צריכה להתבצע דרך תוכניות קטנות ושלמות

זו פרקטיקה גרועה מאוד ללמוד במשך פרק זמן כלשהו ואז מיד לנסות לכתוב תוכנית גדולה.
אני ממליץ ללמוד דרך תוכניות קטנות שאפשר לסיים בערב אחד:

- מחשבון ניסיון לשחקן;
- צ'אט פשוט באמצעות sockets;
- סינון רשימת משתמשים (כאן הצלחתי ללמוד את StreamAPI);
- טיימר למשחק;
- מחולל לוחות זמנים;
- מערכת מלאי פשוטה;
- יצירה אסינכרונית של קבוצת עולמות או פריטי משחק.

חשוב שהתוכנית תהיה קטנה, אבל תבצע מספיק פעולות כדי לקבל את התוצאה הדרושה.
מה שהכי עזר לי היה פיתוח יישומים קטנים או מודים למשחקים עם זרימת נתונים טיפוסית:

1. קלט.
2. עיבוד מידע.
3. עמידות לתקלות ותגובה לשגיאות.
4. פלט.

למשל, לא רק:

```java
int level = 10;
System.out.println(level);
```

אלא כך:

```java
public final class ExperienceCalculator {
  public int experienceForNextLevel(int level) {
    if (level < 1)
      throw new IllegalArgumentException("Level must be positive");

    return 100 + (level - 1) * 35;
  }
}
```

כאן כבר יש התנהגות שברורה למפתח עצמו:

- מה בדיוק נחשב לקלט לא תקין;
- איפה אנחנו מחשבים את הערך;
- איך לקרוא למתודה כך שהשם יסביר את המשמעות שלה;
- מה יקרה אם יקראו לקוד אחרת מהמתוכנן.

אני רואה לעיתים קרובות מתחילים שתוהים בזמן ההרצה: ״איך הקוד שלי יעבוד?״ זה קורה כי התנהגות התוכנית לא תוכננה מראש.

## לומדים דרך שאלות, לא דרך נושאים

בעבר פשוט הצבתי לעצמי מטרה. למשל: ״ללמוד אוספים״.

השאלה של מתכנת הייתה נשמעת אחרת: ״איך לשמור רשימת שחקנים כך שאפשר יהיה למצוא שחקן במהירות לפי השם?״

אלה צורות חשיבה שונות. במקרה הראשון האדם זוכר שמות של מחלקות. במקרה השני הוא בוחר כלי למשימה ומבין את הסיבות הבסיסיות לבחירה הזאת.

למשל:

```java
Map<String, PlayerProfile> profilesByName = new HashMap<>();

profilesByName.put("ZapolyarnyDev", new PlayerProfile("ZapolyarnyDev", 67));

PlayerProfile profile = profilesByName.get("ZapolyarnyDev");
```

אחרי מימוש כזה כדאי לשאול את עצמכם:

- למה כאן `Map` ולא רשימה פשוטה;
- מה יקרה אם השם לא נמצא;
- האם אפשר לשמור את המפתח באותיות גדולות או קטנות אחרות;
- מה יישבר אם לשני שחקנים יש אותו שם;
- איפה עדיף לבדוק ערכים ריקים ולא תקינים.

כך נוכל להבין את החסרונות בקוד ולהסביר את ההתנהגות שלו, במקום לספר מחדש את התיעוד.

## טעויות הן לא דבר רע

אחד ההרגלים החשובים ביותר הוא לא רק לתקן שגיאה, אלא להבין איך היא נוצרת.

תרחיש גרוע:

1. קיבלתי שגיאה.
2. העתקתי את הטקסט לחיפוש.
3. הדבקתי את הפתרון הראשון.
4. הקוד עבד.
5. המשכתי הלאה.

ובשנתיים הראשונות שלי בתכנות זה בדיוק מה שעשיתי :D

תרחיש סביר יותר:

1. קיבלתי שגיאה.
2. קראתי את ההודעה או את הלוג במלואם.
3. מצאתי את השורה שבה היא נוצרה.
4. ניסחתי את הסיבה במילים שלי.
5. תיקנתי.
6. כתבתי מסקנה קצרה.

למשל:

```java
String rawName = null;
String normalized = rawName.trim().toLowerCase();
```

השגיאה כאן לא נובעת מהשפה. הסיבה היא שהקוד מניח שקיימת מחרוזת, אבל ההנחה הזאת לא מוגנת בשום מקום. במקומות כאלה המתכנת צריך לטפל.

תיקון יכול להיראות כך:

```java
public String normalizeName(String rawName) {
  if (rawName == null || rawName.isBlank())
    throw new IllegalArgumentException("Name must not be empty");

  return rawName.trim().toLowerCase();
}
```

לאחר מכן חשוב לזכור לא רק ש״הגנו על קריאה מפני ערך null״, אלא עיקרון כללי יותר:

> אם מתודה לא יכולה לעבוד בלי ערך, היא צריכה לבדוק את הקלט במפורש או לקבל טיפוס שאוסר מצב ריק.

זאת כבר למידה.

## לא צריך לפחד לשכתב קוד

הפתרון הראשון כמעט תמיד עקום. זה נורמלי. יתרה מזאת, הניסיון לכתוב ״נכון״ מיד עלול לעיתים להזיק.

הסכנה מתחילה כשאדם רואה בפתרון הראשון שעובד פתרון סופי. קוד יכול לעבוד ובו בזמן להיות לא נוח,
שביר או לא ברור.

דוגמה לפתרון ראשון:

```java
if (command.equals("start"))
  startGame();
else if (command.equals("stop"))
  stopGame();
else if (command.equals("reload"))
  reloadGame();
else
  sendUnknownCommand();
```

לשלוש פקודות זה בסדר. בשלושים זה כבר יקשה על התחזוקה ועל ההרחבה.

גרסה נוחה יותר יכולה להיראות כך:

```java
Map<String, Runnable> commands = Map.of(
  "start", this::startGame,
  "stop", this::stopGame,
  "reload", this::reloadGame
);

commands.getOrDefault(command, this::sendUnknownCommand).run();
```

אבל גם כאן צריך לחשוב, ולא רק לכתוב פתרונות יפים.
הגרסה השנייה קצרה יותר, אבל לא תמיד ברורה יותר למתחיל. מתכנת טוב לומד לשאול: האם הפתרון נעשה פשוט יותר לשינוי עתידי?

תמיד כדאי לכתוב קוד כך שרוב הנתונים והפעולות בזמן הריצה יהיו צפויים.

## צריך לקרוא קוד של אחרים באופן פעיל

> קריאת קוד של אחרים עוזרת להסתכל בצורה רחבה יותר על מימוש המשימה הדרושה.

למשל, ראינו את המתודה הבאה:

```java
public MatchResult finishMatch(Player winner, Player loser) {
  ratingService.addWin(winner);
  ratingService.addLoss(loser);
  rewardService.giveReward(winner);

  return new MatchResult(winner.id(), loser.id());
}
```

לפני שמסיקים מסקנות, עדיף לשאול עוד כמה שאלות:

- האם אפשר לקרוא למתודה פעמיים;
- איפה בודקים שהמשחק באמת פעיל;
- האם המפסיד צריך לקבל פרס ניחומים;
- האם צריך להביא בחשבון את ההקשר שבו המתודה נקראת;
- מי שומר את התוצאה.

כך אפשר לאמן את היכולת להבין טוב יותר את אופן הפעולה ואת הדקויות של רוב הטכנולוגיות.

## פרויקטים קטנים צריכים לגדול

כבר עסקנו למעלה בפרויקטים לימודיים. פרויקט לימודי טוב לא חייב להיות גדול, אבל צריך להוסיף לו בהדרגה דרישות ומטרות.

למשל, המשימה הלימודית הטיפוסית ביותר: ״לבנות אפליקציית TODO״.

v0.1:

- להוסיף משימה;
- להציג רשימת משימות;
- לסמן משימה כהושלמה.

v0.2:

- לשמור את המשימות בקובץ;
- להוסיף מועד אחרון;
- לסנן משימות שהושלמו;
- לטפל בקלט ריק.

v0.3:

- לכסות את הפעולות המרכזיות בבדיקות;
- להפריד את האחסון מהלוגיקה;
- להוסיף ייבוא וייצוא;
- ליצור ממשק פשוט.

צמיחה כזאת מלמדת לתכנן את הארכיטקטורה של התוכנית או היישום הרבה יותר טוב מאשר ניסיון לכתוב הכול בפעם הראשונה.

## איך ללמוד כל יום

בדרך כלל מפגשי הלמידה שלי ארכו 60–90 דקות ונראו בערך כך:

1. לבחור תוצאה רצויה אחת.
2. לכתוב את הקוד ״כמו שהוא״.
3. להריץ ולבדוק אותו עם הרבה קלטים לא תקינים.
4. לתקן את השגיאות שנמצאו.
5. לשכתב את התוכנית בהדרגה, בחלקים ובצורה נכונה יותר.
6. לכתוב שלוש מסקנות.
